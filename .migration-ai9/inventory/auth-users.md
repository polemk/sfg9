# Inventário — auth & users (IDs 001–049)

> Legado: `sfg` (Rails 6.1.4 / Ruby 3.0.2), monolito + engines `livetat` (`engines/auth19`, `engines/auth_omni19`, `engines/auth_ux19`).
> Stack de auth: **Devise 4.6** (`database_authenticatable, registerable, recoverable, rememberable, trackable, validatable, omniauthable`) + **simple_token_authentication** (token de usuário e de aplicação cliente) + **pretender** (impersonation) + **Paperclip** (avatar).
> **Não existe CanCan/Pundit.** A autorização é um sistema próprio: `RoleType` → `Role` → `Ability` (registros no banco), materializados por `Livetat::Auth::AbilityFactory`, e consultados via `user.may?("<nome>")` / `user.<nome>?` / `user.how_many(...)`.

- lacunas/dúvidas para o Phase 2:
  1. **Autorização praticamente inexistente no backend.** Impersonation (BE-031), update/delete de usuário (BE-013/BE-014/BE-030), alteração de abilities (BE-018/BE-042) e memberships (BE-045/BE-046) não checam nada — os gates estão só nas views.   2. **`RoleType` default quebrado.** `Livetat::Auth.config.default_role_type = "Visitor"` e `minimal_type_to_sign_up_through_web = "Manager"` referenciam tipos destruídos pelo seed do app. Precisamos do dump real de `livetat_auth_role_types` (nomes e `hierarchy`, em especial de `Gerente`) para reproduzir as regras de login e de `role_types_for_filter`.
  3. **Token de reset de senha nunca expira** (BE-020: o token só é gerado quando `reset_password_sent_at` é nil). Definir a política nova (expiração real, invalidação após uso, one-time token).
  4. **Rotas/actions inexistentes ou mortas**: `GET /u/console/users/id` → `users#detail` (action não existe); `show_info` (rota sem action, BE-015); `Pub::PermissionsController#index` renderiza `pub/permissions/index` inexistente (BE-040); redirect pós-login para `/u/console/profile` (FE-002). Confirmar com logs de produção o que realmente é acessado.
  5. **Dois fluxos paralelos de recuperação de senha** (painel embutido vs. páginas Materialize da engine) e **duas telas de reset**. Decidir a canônica.
  6. **`is_active` × `deactivated`**: dois campos de "conta ativa". Confirmar qual é a verdade e o que fazer com `legacy_password` (hash Django) na migração.
  7. **`update_attributes` no `update_info` (BE-016)** não existe no Rails 6.1 — verificar se o endpoint está morto ou se há monkeypatch em algum lugar não lido.
  8. **Login por Facebook (BE-023/OPS-007)**: credenciais default são placeholders e não há botão renderizado. Confirmar se a feature está ativa antes de portar (inclusive o `provider_ignores_state: true`, que é vulnerabilidade).
  9. **`ClientApplication`**: não existe CRUD na aplicação. Descobrir como os registros são criados hoje (console? seed? manual no banco?) e quais integrações usam `X-LAA-*`.
  10. **Abilities do tipo `limit` (`max_*_amount`) e as `may_*_entries`** existem no modelo e nos seeds mas não gateiam nenhum comportamento observável. Decidir se migram como conceito ou se são removidas.
  11. **Papéis de membership** (`Responsável`, `Coordenador`, `Gestor`) não têm UI. Confirmar se são usados por algum processo/relatório fora da área de auth.
  12. **`include_ability_methods`** define métodos na classe `User` em runtime a partir dos dados do banco (`may_create_users?`, `max_users_amount`, ...). Se uma ability for removida, as views quebram com `NoMethodError`. Definir o modelo equivalente e seguro no ai9.
