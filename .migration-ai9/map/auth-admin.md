## Legenda das estratégias

| Valor | Significado |
| ----- | ----------- |
| `reuse` | A base ai9 provê isto **como está**. O trabalho é apontar e configurar. |
| `adapt` | A base tem algo próximo. Estender (campo, regra, variante, gate). Não reimplementar. |
| `build` | Não existe na base. Implementar novo, idiomático ao ai9 — **sempre sobre a infra citada na coluna "Equivalente ai9"**. |
| `drop` | Comprovadamente código morto ou revogado por decisão. **Vai para o `parity-ledger.md` como `dropped` com a evidência da linha** — nunca por omissão. |
| `build?` | Eu **não** tenho certeza se a base provê. A dúvida está escrita na linha. Confirmar antes de estimar. |

`drop` não é uma quarta estratégia inventada: as três specs deste bloco já mandam descartar
com evidência (`ENG-navkit`, `ENG-auth_omni19`, BE-004, BE-537, FE-539…). Marcar essas
linhas como `build` seria mentir sobre o trabalho.

## 0. O item de maior risco deste mapa: **a escala de hierarquia está invertida**

> Leia isto antes de qualquer outra coisa. É o defeito que **passa em teste** e **dá poder de
> OG a um Colaborador**.

| Sistema | Convenção | Evidência |
| ------- | --------- | --------- |
| **Legado sfg** | número **maior** = mais poder | `../sfg/db/seeds.rb:40-95` e `../sfg/engines/auth19/db/seeds.rb:9-29`: `OG 1111` > `Admin 998` > `Gerente 888` > `Colaborador 799` |
| **Base ai9** | número **menor** = mais poder | `backend/app/models/user_type.rb:38-41` (`OG hierarchy_level: 1`, `client: 2`, `free: 4`, `visitor: 5`) e os scopes em `:19-21`: `higher_than` é `where('hierarchy_level < ?')`, `lower_than` é `> ?`, `ordered_by_hierarchy` é `asc` |

**Por que isto é o item mais perigoso.** As decisões **DEC-18.2** (Permissões: Admin edita só
papéis de hierarquia **inferior**) e **DEC-18.3** (impersonation: Admin personifica só
hierarquia **inferior**) dependem inteiramente do **sinal** dessa comparação. Inverter o
sinal **dá poder de OG a um Colaborador** — e passa em qualquer teste que verifique apenas
que "a trava existe", porque ela existe: só está apontando para o lado errado. É uma falha
que se lê como correta.

**Decisão: adotamos a convenção do ai9** (menor = mais poder). Princípio 6b — `UserType` é
peça da base compartilhada, e outros sistemas dependem desses scopes.

**De-para do ETL — tabela explícita, nunca fórmula:**

| Papel | `hierarchy` no legado | `hierarchy_level` no ai9 |
| ----- | --------------------- | ------------------------ |
| OG | 1111 | **1** |
| Admin | 998 | **2** |
| Gerente | 888 | **3** |
| Colaborador | 799 | **4** |
| *(papel vazio `""` — D-36)* | — | **4** (entra como Colaborador **e sai na lista de exceções** para revisão humana, DEC-18 #8) |

Fórmula é perigosa aqui: qualquer aritmética (`5 - x`, normalização por ordem) sobrevive a
um valor inesperado no banco e produz um nível plausível e errado. **Tabela de-para falha
alto** quando aparece um `hierarchy` que ninguém previu — que é exatamente o que se quer,
já que o dump de `livetat_auth_role_types` não existe (DEC-04) e a hierarquia do Gerente
sequer aparece explicitamente no trecho lido do seed (DB-006).

**Teste obrigatório — sempre os dois lados, nunca só um:**

- `Admin` **NÃO** consegue editar ability de `OG` · `Admin` **CONSEGUE** editar ability de `Colaborador`
- `Admin` **NÃO** consegue personificar `OG` · `Admin` **NÃO** consegue personificar outro `Admin` (lateral) · `Admin` **CONSEGUE** personificar `Colaborador`
- `Gerente` **NÃO** alcança a tela de Permissões (DEC-18.2 tira o Gerente de lá)
- O filtro de usuários de um `Gerente` **NÃO** devolve `OG` nem `Admin`

Um teste que só afirma "existe 403 em algum caso" **não** detecta a inversão. O par
positivo+negativo detecta.

**Toda linha deste mapa que toca hierarquia está marcada com risco `alto`:** DB-006, DB-502,
BE-504, BE-025, BE-031, BE-042, e o seed de OPS-009.

## 0.1 O que este bloco decide para o resto da migração

Três decisões deste mapa são **fundações** — todo outro bloco constrói em cima delas:

1. **Membership de projeto** (S4). O escopo por projeto do DEC-07 — recebíveis, empresas,
   renegociações, operações de risco — só existe se `Membership` existir. A base ai9
   **não tem multi-tenancy nenhum** (`ai9-conventions.md` §4; zero `tenant_id` em 52 tabelas).
   É `build`, e é a peça de maior alcance do bloco inteiro.
2. **Autorização declarativa por rota** (S3). A matriz aprovada (45 recursos × 4 papéis)
   vira um helper de servidor. Hoje a base só tem `require_og!` e `restrict_visitor_access!`
   (`backend/app/controllers/api/v1/controller_helpers.rb:37,44`).
3. **Login sem senha** (S2). O legado autentica com Devise + senha; o ai9 **não tem senha**
   em lugar nenhum. Isso muda o que o usuário vê no dia 1 e está registrado como melhoria
   observável (IMP-A1 abaixo).

### 2.10 `engines` — o veredito por engine (antes da tabela)

**Engine não se porta como engine.** As 7 engines locais do legado são um mecanismo de
reuso entre produtos da Livetat, e o ai9 **já é** esse mecanismo de reuso: é a base
compartilhada. Portar `auth19` como engine dentro do ai9 seria criar uma segunda base
compartilhada dentro da primeira. Então cada engine é decidida por **destino**, não por
tradução:

| Engine | LOC/alcance no legado | Destino no ai9 | Por quê |
| ------ | -------------------- | -------------- | ------- |
| **`auth19`** (núcleo de identidade) | `User`, `RoleType`, `Role`, `Ability`, `UserInfo`, `ClientApplication`, config do Devise | **Vira infraestrutura do ai9 que já existe** — `User`, `UserType`, `Permission`/`UserPermission`, `ClientApplication`. É o maior ganho de reuso do bloco. | O ai9 já tem identidade. Duas identidades no mesmo app é o pior resultado possível. |
| **`auth_ux19`** (camada HTTP/UX de auth) | controllers de sessão, cadastro, senha; ~15 telas | **Some.** O HTTP vira `api/auth/v1/*` (existe); as telas viram `features/auth/*` (existe). Zero tabelas próprias (DB-507). | É a camada que o ai9 substitui inteira. Das ~15 telas, 9 são duplicatas (**D-42**) ou inalcançáveis. |
| **`auth_omni19`** (login social) | OmniAuth Facebook, `Provider` | **Some como engine; a função vira `api/auth/v1/oauth.rb`** (existe, com Google **e** Facebook). A tabela `livetat_auth_omni_providers` vira 2 colunas em `users`. | A engine está **morta** no legado (`app_id = 0`, botão não renderizado, **D-41**), e o ai9 tem OAuth melhor. |
| **`feedback19`** (mensagens/tickets) | `Message`, `Note`, `Context`, `Observer`, `State`, notificações | **Vira código do app** (S9). É domínio pequeno e específico do produto, não infraestrutura. | Não há nada parecido no ai9 e não deveria haver: é feature de produto. |
| **`mailer19`** (envio de e-mail) | `GrindMailer`, `Mailing`, SMTP, DKIM, log de envios | **Vira `ApplicationMailer` + Sidekiq** (existe). O log de envios é decisão à parte (DB-514). | ActionMailer + Sidekiq já é a camada de e-mail do ai9. Uma fachada própria em cima só acrescenta um lugar onde o e-mail se perde (**D-78**). |
